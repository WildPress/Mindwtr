# Android native development app

This isolated Compose app uses `tech.dongdongbh.mindwtr.nativeclient.dev` and its own private `mindwtr-native-dev.db`. It does not read or replace the React Native app. It has RN's tabs: **Inbox**, **Focus**, the quick-access tab (**Review**, **Contexts**, **Calendar**, or **Projects**, as core's setting names), and **Menu**. Each list shows its first 50 rows, loads more in windows of at most 50, and calls the shared core contract to capture, complete, and edit tasks. The app has no sync, external intents, fixture seeding, or production upgrade path.

Every word on screen comes from core. At boot the app calls core's `setLanguage` with the React Native app's saved language (AsyncStorage `mindwtr-language`, read by the upgrade build's guard; none in the dev build) and the device locale, then reads one label map through `getStrings`. The keys are the ones mobile uses for the same controls (`Labels.kt`). Core fills in English for a key a language lacks; a key core does not know shows as the key and is logged once. Core has no key for "Refresh", "Load more", "Reload", or "Storage unavailable", so the app uses **Try again** (`common.retry`) for a failed read and for the editor's reload, **More** (`common.more`) for the next window, and shows a failed boot as its message alone.

The app looks like the React Native app, so an RN user recognizes it at once: RN's header, RN's bottom tab bar (Focus, Inbox, the center capture button, the quick-access slot, and Menu), RN's theme tokens (`Theme.kt`, the only file with colors), RN's lucide icons (`Icons.kt`), and RN's task row (`TaskRowView.kt`). A row shows core's meta line as core sent it (project or area dot, contexts, the due date in the user's format and core's urgency color, the checklist count; detail parts stay hidden, as in RN's lists and default Focus), core's priority strip, and core's TalkBack label. A swipe right reveals RN's labelled action button for the row's status (Done, Next, or Restore, from core's row meta): a tap runs it and a long-press opens RN's status menu, as in RN. TalkBack has the same action and Change Status as custom actions; there is no Done button, as in RN. The Inbox shows RN's status glyph and a project shows RN's status badge; a tap opens RN's status menu, which saves through core's `updateTask`. The header's left side is RN's area switcher (`AreaSwitcher.kt`): core's `getAreaFilter` label, and RN's sheet, where a tap sends core's `next` selection through `setAreaFilter`. A refused star shows core's text in RN's toast. The capture button opens RN's capture popup (`CaptureScreen.kt`) on core's quick capture contract (`native-host-contract-quick-capture.ts`): Add Task and Close, the field with core's live preview, the project or contexts chip with Focus and More, More's panel (the note, the Focus, due time, contexts, area, project and priority chips with RN's pickers, the syntax help, and Today, Tomorrow, Next week and Custom; the Custom date and due time pickers open on core's day and time), and RN's Add another switch (RN's Android switch: a raised thumb on a faint track; kept on the device under RN's key) with Save & edit and Save. Every chip and picker row sends the edit core put on it. Several lines ask core's question; Create tasks writes core's recovery snapshot under `files/snapshots` (as mobile does: a temporary file, a clash number, the 5 newest) and then one task per line in one write; the batch sends the name actually written, which is on disk with the request, so a retry sends the same snapshot and a stale one is replaced with a new snapshot and the same capture UUIDs. Each save's exact request (a capture UUID, one per line for several lines) is written to a synced file in the no-backup folder before the call; a failed one keeps its exact retry, and after process death it is sent again before anything else, so core writes it once. A refused date command shows core's notice and keeps the draft. The popup's draft (text, options, open picker, and chip edits not yet answered) survives rotation and process death; a request whose outcome was lost comes back even after a force-stop. Close discards the draft, as RN does. In portrait only More's panel scrolls, as in RN; in landscape everything under the header scrolls, so Save & edit and Save stay reachable above the keyboard. RN's microphone and Import .txt are not built. The theme is RN's choice as core resolves it: the synced `settings.theme`, else RN's device-local `@mindwtr_theme` (read by the upgrade build's guard), else the system's light or dark mode.

Each screen scrolls as one list, so landscape shows rows rather than fixed controls. The Inbox is RN's task list on core's `getInboxView`: its first items are RN's Sort, Group and Filters controls (Filters in the tint with core's count while filters are on) with the Mind Sweep pill beside them, the active filters with Clear, RN's **Process Inbox (N)** button (core's label, 99+ above 99; TalkBack hears core's exact count), and core's "All areas" line. An empty Inbox shows Mind Sweep in the button's place. Mind Sweep (the pill, the button, and the Weekly Review's links) opens RN's full-screen Mind Sweep on core's `getMindSweep` and `addMindSweepItem`: core's title and Close, the intro with core's scope chips and Start, one cue list at a time (its title and progress, the prompts, the capture box with Add, core's failure line, what was captured in it, Back and Next), and the summary with Finish. Each control carries core's scope or step. Add waits for core's answer on the text as typed, then sends it with a request UUID that becomes the Inbox task's id; the request is in a synced file in the no-backup folder before the call, so a failed Add keeps its exact retry and a lost answer is sent again first after process death. The screen state (scope, step, captures, the text, the failure line) is in a synced file while Mind Sweep is open, so rotation and process death keep it; Close and Finish forget it, as RN's modal does, and return to the screen it opened over. Sort is the stored task-list sort (`setTaskListSort`); the grouping and the filters are RN's session choices; a folding heading keeps core's folds for its grouping under RN's `mindwtr:view:group-collapse:inbox:v1`. Only the header, the tabs, a failure message with its retry, and the bulk bar while selecting stay fixed.

A long-press on a row of the Inbox, Waiting, Someday, Reference or Done starts RN's selection mode on core's `getBulkActions` and `runBulkAction`: a tap toggles a row (core keeps the tap order and Range's anchor), and RN's bulk bar shows core's count, core's statuses to move to, Move to section… (Someday), Bulk organize (the Inbox), Range, Add tag, Remove tag, and Delete, which asks core's question first and whose toast has core's Undo. The bar also offers core's stateless Select all (RN's lists have none; the contract has it, as Archived does): core resolves it again for the action and refuses it once the rows changed. Bulk organize is RN's dialog on core's draft: every chip, picker row, quick date and typed field sends core's edit, and Apply sends the draft core answered. An action that changed something leaves selection mode; Back leaves it too. Read-only rows (an archived project's) never select.

The header's search button opens RN's global search on core's `searchTasks`: the field, Clear, RN's filter sheet (due date, location, contexts and tags, Include, status, scope, area, all core's words and choices), the active chips that clear a filter, core's truncation and hidden-matches lines, and the project and task results with core's highlights and date line. A task opens the editor over the search, and, as RN's highlight, its row on the list it opened on (the one under the search) is outlined in the tint until 3.5 s pass or that list is left; a result core cannot open there goes to its list (Inbox, Focus, a project, or the Menu tab's Waiting, Someday, Reference, or History's Done or Archived). Clearing an active chip removes its filter value, so a second tap changes nothing. Mark Done is the lists' Done. Save Search saves through core's `saveSearch`: the submitted query, name and request UUID are kept with the screen before the call, the dialog stays locked to them until core answers, and after process death they are sent again before it unlocks. Save Search stays on the search (RN then opens the saved search's screen; not wired yet). An answer for an older query is dropped by core's echoed query.

**Process Inbox (N)** opens RN's step flow on core's session (`startInboxProcessing`, `getInboxProcessingStep`, `commitInboxProcessingStep`, `skipInboxProcessingTask`, `endInboxProcessing`): the progress header with Close, RN's guided/quick switch (kept on the device under RN's key `mindwtr:view:inboxProcessingMode:v1`) and Skip; the item's card with its editable title and note; then core's step, drawn from core's view, where every chip, date, and suggestion sends the exact edit core put on it, one at a time. Each answer (a choice, File it, Back, Skip) is a command with a request UUID: it is written to a synced file in the no-backup folder before the call, a failed one keeps its exact retry through rotation and a new screen. After process death the app lands on the Inbox, as RN does, and the owed answer is sent again in the background: core's session died with the process, so core refuses it without writing and its message shows. The record on disk goes only after core acknowledges or refuses the answer, so another death during that replay finds it again. Core refuses a new session while earlier writes are unsaved; its message shows. The failure message is drawn above the list and is a live region, so TalkBack always reaches it.

The **Menu** tab opens RN's More sheet on core's `getMoreMenu` (RN's `MoreNavigationSheet`): over the list and above the tab bar, a dimmed backdrop and a card with RN's handle, core's utilities (Trash, Board, History, Settings), core's saved searches, and core's six tiles, with RN's Ionicons in core's colors. A drag down, the backdrop, Back, the Menu tab again, another tab, or the capture button closes it. Waiting, Someday, Review, Reference, Contexts, Calendar, Board, History, Trash, Projects, Settings, and the saved searches open. A saved search opens RN's screen on core's `getSavedSearchView` under RN's stack header (Search): its name, its query, and Delete (RN's red trash), which asks core's question and then sends core's `deleteSavedSearch` and goes back; core's rows with the lists' own swipes, status menu and editor (windows of 50, **More**); and core's empty line, with core's Inbox and Back when the saved search is gone.

The quick-access slot of the tab bar holds the view core's `quickAccessView` names, as in RN: **Review** (RN's default), **Contexts** or **Calendar** show that screen under the tab header, and Projects then moves to the More sheet, where its tile opens RN's Projects screen (a parked, archived, or searched project opens there too). Any other value shows Projects. The app reads the sheet at boot, so the tab bar draws the right tab from its first frame. A destination opens full screen over the tabs, as RN pushes it, under RN's stack header (Back and the title); Back returns to the tabs. Each list reads core's view in windows of 50 (**More** at the end) and each collection (people, parked projects, filter tokens and projects, saved searches) in core's windows of 100 through `getMenuViewCollection`, under the view's revision; a view that changed between windows is read again from its first window. Rows are RN's task row with RN's status glyph, and every list is read again on resume and after every command.

Differences from RN on purpose: the bulk bar of the Inbox, Waiting, Someday, Reference and Done offers core's stateless **Select all** (RN's task lists have none; the contract offers it, as Archived's bar has); on Focus's reorder screen only the dragged row moves and shows its new place (RN also slides the other rows aside; the stored order is the same); Mind Sweep's Back and Next go to the step core put on the control, so a quick double tap moves one step (RN's functional update moves two); Mind Sweep keeps text typed while an Add was with core (RN empties the box anyway); the Focus checklist page writes a rename once the previous edit's answer is in, so fast typing is one write per round trip rather than one per keystroke (each edit is compare-and-set on the task revision core answered, so edits go one at a time), and core's list shows again after core refuses a stale edit; and a failed bulk action shows the failure message with its exact retry rather than RN's "failed" toast, as every write here does.

From the repository root:

```sh
bun install --frozen-lockfile
node apps/android-native/scripts/build-bundle.mjs
cd apps/android-native/android
./gradlew :app:assembleDebug --offline
```

The build also regenerates `core-host.js` from current core source. Install only the resulting development APK (`android/app/build/outputs/apk/debug/app-debug.apk`) into the isolated development package. A clean install creates an app-private SQLite checkpoint before core schema setup. On later launches, the first checkpoint is retained. The checkpoint file and its directory entry are synced before task writes. Every core data load is checked against storage row counts, including the load during contract activation. A failed check shows only the failure message and offers no command. A capture that fails keeps its draft locked to its exact retry (the same capture UUID).

The checkpoint is a SQLite `VACUUM INTO` snapshot, so it includes committed WAL content. This development app has no other recoverable user data yet. It is not a tester build: its log is only in logcat, and it has no Settings › Diagnostics. A tester build needs that diagnostics screen, upgrade and recovery validation, and the remaining workflows before distribution.

The adapter rejects detected concurrent database writes, so the process owns exactly one core host (`ProcessCoreHost`). Activities and the Inbox `ViewModel` never close it; process death is the only shutdown. Screen state lives in the `ViewModel`, so rotation keeps an in-flight or failed save. A failed command's exact retry also stays with the process host until that retry succeeds, so a screen that is closed and reopened in the same process shows the failure and its retry again. The capture popup's draft survives process death on disk, and a capture whose outcome was lost is sent again with its capture UUID, so it is written once. `am force-stop` discards that saved screen state by Android design, but an owed capture on disk still comes back and is sent again.

Tapping a row opens the React Native task editor's Form tab. It reads core's `getTaskEditorModel` (the draft, the fields to show by section in the user's order, which sections start open, their filled counts, and every list a control picks from) and saves through core's `saveTaskDraft`; Kotlin holds no task rules. The header has RN's Close and Save; the title, then core's fields with RN's controls: status chips, the Destination picker (project or area), the section picker, the Someday section chips, the date rows (a date, or a date and a time from the clock button), context and tag fields with core's suggestions and quick chips (`getTaskEditorSuggestions`), priority, energy and time-estimate chips, the recurrence rule and "Repeat after completion", Skip reminders, assigned person, location, and notes. Every control's edit goes to core's `editTaskDraft`, one at a time, and the editor then shows the model core returns for the edited draft: its fields, sections and choices follow the draft as the user edits it. Dates show core's labels in the user's settings; a picked day keeps an existing time, the time picker starts at core's time for the field, and RN's quick date chips, Date only, the starts-after-due warning, the relative start (core moves it with the due date), the recurrence interval, days and ends, the repeat reminder intervals, and the custom time estimate all write core's values. Kotlin only turns the picker's day and time into `yyyy-MM-dd` and `HH:mm`, and core's picker start back into the picker. Typed text (title, notes, location) stays in the editor until Save. Attachments and RN's custom monthly rule are shown read-only. The **checklist** is RN's field on core's `editTaskChecklist` field model: the checkbox, the title as typed, ×, Return (a new item after it, focused as core names it), "+ Add item", Reorder with Move up and Move down, and Reset checklist. Every change is core's checklist edit on the editor's draft checklist, queued with the draft's own edits (a list task's status follows its items, as core decides), and Save sends the checklist with the draft fields in core's one `saveTaskDraft` write (its base is the checklist the editor loaded, from core's `getTaskView`). Reset checklist writes at once, as in RN (core's `resetTaskChecklist` with a request UUID and its exact retry), then the reset task becomes the editor's base and the editor's own items reopen. RN's **tabs** (Edit and Preview) sit under the header: the **View** tab is core's `getTaskView` for the draft and checklist as they are now (the saved task when read-only), read again whenever they change: the title, the status (a tap opens the statuses, with the Form tab's Waiting prompt), core's facts, contexts and tags (a tap opens Contexts with that chip), the notes drawn from core's resolved Markdown blocks (headings, lists, task lists, code with its copy button, rules; bold, italic, struck, code, and links: a web, mail or phone link opens outside the app, a task or project link leaves the editor as Close does, asking first when there are unsaved edits), the checklist (a tick is core's toggle; core's add input appends on Done; More reads core's next window of 100), and the attachments listed with core's notes. A read-only task (an archived project's) shows only its View tab. The editor opens on the tab RN's `resolveTaskOpenTab` picks: the View tab for a read-only task; the Form tab for RN's explicit edits (Save & edit, the Board's Duplicate, the Weekly Review's Add task and edit); else the device's Open tasks in choice; else the list's own tab: the Inbox list opens the Form tab (RN's `defaultEditTab="task"`), and every other screen, a search result and a task link open the View tab. A checklist edit names its item by the item's id (a move by its direction); the item's position is read only when the edit is sent, after the edits queued before it, and an edit whose item is gone is dropped. The open tab and the edited checklist are kept with the draft on disk, so rotation and process death keep them. Save sends only the changed draft fields, each with the value it was loaded with, and closes without a call when nothing changed; typed context, tag, and person text waits until core has said which draft value it stands for. If another writer changed a field you edited, core refuses the save, the draft stays, and **Try again** takes the stored value of each changed field while keeping your other edits. A failed or timed-out save locks the draft to its exact retry, like a failed capture. Leaving with unsaved edits asks Discard / Save / Cancel, as the mobile editor does. Typed text core has not resolved counts as an unsaved edit. Choosing Waiting first asks who or what it waits for, as RN does. The draft (its edits with the values they were loaded with, and the typed text) is kept in a synced file in the app's no-backup folder; saved instance state holds only that file's key. After process death core's model is read again and the draft goes on top, so a save still detects another writer's change. A save's exact request is written to that file before the call; if the process dies before core answers, the relaunch sends it again before the draft unlocks, and core writes nothing twice.

The **Focus** tab shows core's `getFocus` reply as it is: core's sections in core's order, with core's titles and totals, and each section's first 50 rows. **More** reads that section's next window through `getFocusSectionWindow`. Kotlin holds no Focus rules: it never sorts, filters, or groups rows, and it never reads a date. It uses only two row flags from core. A **Later today** heading goes before the first row core marks `laterToday`, and an Upcoming row shows core's `revealLabel` text as it is. Above the sections is core's date line (`dateLabel`) with RN's View options, Filters (core's count on a badge) and Focus only / Expand sections buttons, then core's saved Focus filters (All, each filter with its delete button; a long-press deletes too, after core's question) and the active filters with Clear. Every Focus read sends the control state core last answered (`controls`: the filters, the applied saved filter, the sort) and a control's edit (`controlEdit`), so core's grouping, sort and filters shape the sections; Next actions under a grouping shows core's headings, with the rows under them indented. View options holds core's sort chips, the group chips (core's `setFocusGroupBy`) and Show details (kept in RN's JSON). The filter sheet is core's (no search box, as in RN), with Save (core's `saveFocusFilter`: its request UUID becomes the filter's id, kept in a synced file in the no-backup folder before the call and sent again first after process death) and an applied saved filter's own criteria, which ask before core removes them. While core allows it, Today's Focus has RN's Reorder: a screen of core's rows where a long-press and drag moves a row and the drop sends core's `reorderFocus` once (TalkBack has core's Move up and Move down). The control state, the open sheet and reorder mode survive rotation and process death. A section core counts as empty is not drawn, and "Projects to review" follows the task sections when core lists any. A tap on a section title folds it; which sections are open is kept on the device under RN's key `mindwtr:view:focus:v1`, in RN's JSON. Each row has RN's star (core's `setTaskFocus`; drawn disabled with core's `focusBlockedLabel` where the section sends one, as on Upcoming); a review-due row also has RN's status badge. Focus changes with the clock, so the app reads it again from the first row when the screen resumes, once a minute while Focus is on screen, and after every command. A refresh keeps each section as deep as More left it. If Focus changed before a More (core answers `STALE_REVISION`), the app reads Focus again from the first row; this is not an error. Complete (core's **Done** label) and the editor work from Focus exactly as from the Inbox, with the same exact-retry lock after a failure. Save and Cancel return to the tab the editor was opened from. The selected tab survives rotation and process death. A failed command's retry keeps its tab and rows, so a new screen reopens on Focus if the failure happened there.

The **Focus checklist page** is RN's `check-focus` route on core's `getFocusChecklist` and `editFocusChecklist`: Back, the task's title, each item's checkbox, its text (struck through once done) and Delete, core's empty line, and Add Item. Every tick, rename, delete and add is core's edit, written at once with the task revision the last answer (or core's page) gave, named by the item's id and placed right before it is sent; a stale edit (a later edit, another device) is refused and the page shows core's list again, and a write that did not land shows RN's error toast with core's words. The waiting edits belong to their task, not to the page: they are in a synced file in the no-backup folder, the edit with core is an exact request on disk before it is sent, an answer moves the queue on whether the page is open or not, and after process death that request is sent again first with its original revision (a failed save keeps its exact retry), then the rest go on. A page (or a Mind Sweep capture list) whose later window went stale is read again whole from its first window, at most three times, then core's failure shows. RN pushes this route only from the task editor's `onFocusMode`, which RN's editor never calls, so no RN control opens it; here a debug build opens it from a launch extra (`--es focusChecklistTaskId <task id>`) for the device check, and release builds never read it. Focus's filter pickers have RN's search box: core's matching contexts and tags or projects (`getFocusControlsList` with `query`, from the first window at Focus's revision, read again when Focus changes). Bulk organize's project and area pickers offer core's "+ Create" row for a name no option carries, and the keyboard's Done runs core's `submit` (the match, or the create): `createBulkOrganizeDestination` makes it under the request UUID (a create, on disk first) and the dialog shows core's draft with it chosen; a create that failed shows core's line.

The **Projects** tab starts with RN's **Add new project…** field: + (or Done on the keyboard) runs core's `createProject` with the area chosen on RN's area chips (by default the one area the filter selects). The draft, its area, and its request UUID survive process death; a failed create keeps its exact retry, and after process death the draft comes back but nothing is sent until + is tapped again. Then core's `getProjects` groups as they come: Active, then Someday / Waiting and Closed, which start closed and open on a tap, as on mobile. Each area header is core's area name (**No area** without one) with RN's colored dot and chevron, and folds its projects. Open groups and folded areas are kept on the device under RN's key `mindwtr:view:projects:v1`. A row shows the title, core's next action, its "No next action" warning, or core's status line, then core's active task count and RN's star (core's `setProjectFocus`, dimmed and disabled when five projects are starred). Tapping a project opens core's `getProjectDetail`: section markers and task rows in core's order, core's sequence cue under a row, and **More** for the next window. If the project changed between windows (core answers `STALE_REVISION`), the app reads it again from the first item. A row opens the editor and swipes to Done, except in an archived (read-only) project, whose rows have no swipe and a disabled status badge, as mobile does. Back returns to the list. The open project survives rotation and process death, and it is read again on every resume and after every command. A failed Done in a project keeps its exact retry, as on the other lists.

While a command's retry is owed, every screen's failure message offers **Try again**, which sends that exact request again, so a command started where its control is gone (a status change from the menu on Focus) stays retryable.

Reads the app starts on its own (on resume, each minute, and after every command) never disable a control, so a tap during one still runs; the engine thread queues both. Each read takes a number, and a command outdates every read that started before it, so an older result is never shown over a newer one.

Debug builds read three fault properties before each create, complete, or update command, and one language property at boot; release builds never read them:

- `debug.mindwtr.native.fail_commit=1` makes every SQLite `COMMIT` fail.
- `debug.mindwtr.native.delay_before_ms=<ms>` holds the command before it runs.
- `debug.mindwtr.native.delay_after_ms=<ms>` holds the acknowledgment after the commit.
- `debug.mindwtr.native.language=<code>` replaces the saved language (for example `zh`) for the next process, so a check never changes the phone's language.

The `upgradetest` build type (`./gradlew :app:assembleUpgradetest`) is for the upgrade harness only. It installs as the throwaway package `tech.dongdongbh.mindwtr.upgradetest` over a real RN v1.3.2 build and opens the RN database, `files/SQLite/mindwtr.db`. Before anything opens that file, a guard refuses to start when the database is missing while other RN state exists and RN AsyncStorage (`databases/RKStorage`) holds no JSON backup, when that backup is over 64 MB, or when either file cannot be read or the database fails `quick_check`. The guard reads byte copies in the cache folder, never the files themselves. On a refusal the app shows the refusal message and changes no file. Otherwise the JS host imports the backup as RN's next launch would (core `planLegacyJsonImport`: the `mindwtr-data:json-ahead-of-sqlite` marker, the one-time reconcile, or an empty or missing database). After the import is saved and read back with every field equal, the guard copies `RKStorage` once to `files/SQLite/RKStorage.prewrite/`, then deletes the marker and/or sets the reconcile flag in one transaction. If either step fails, the app shows the failure message and makes no native write; the next boot retries only the `RKStorage` change. `node scripts/build-upgrade-harness.mjs` builds and signs the three harness APKs; `node scripts/check-upgrade-device.mjs <adb-serial>` runs the upgrade, JSON-backup import, damaged-database, missing-database and RN recovery scenarios on a phone. See the Harness section of `docs/development/native-android-upgrade-inventory.md`. `node scripts/capture-parity-screens.mjs <adb-serial>` uses the same harness APKs to shoot Inbox, Focus, Projects, one task's editor, global search, Process Inbox's first step, the capture popup, the Menu tab (the More sheet, Waiting, Someday, History's Done, Contexts, Trash, and Review), the Weekly Review's first step, the Calendar's week and month, and the Board in light and dark mode, first in RN 154 and then in the native build, on one fixture database built through core, and writes side-by-side PNGs (RN left) to `/home/dd/.mindwtr-harness/parity/<timestamp>/`.
